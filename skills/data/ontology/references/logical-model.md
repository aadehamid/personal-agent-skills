# Adding a logical data model exported from a modelling tool

Serves a new module, or a new model in an existing one, built from a logical data model that a modelling tool exported as RDF. Read it with `new-module.md`, whose rules and step table still apply; this file narrows them for a logical model.

Some relational modelling tools export a logical model as Turtle, natively or through an add-on: each entity an `owl:Class`, each attribute an `owl:DatatypeProperty`, all in the tool's own namespace, sometimes with the tool's own SHACL shapes for the keys. Check what your tool writes before you rely on any of this; the rules below say where the method depends on it. The method keeps that export as the tool's view and adds one layer that links it to the ontology.

## Decide the shape

1. **Hold every logical model in one module, with each export as one named model inside it.** A later export joins that module as another model; it does not become a module of its own, and it is not a release of the module that holds the platform's tables or data products. Name the model and the module in the decision record (`new-module.md`, rule 3). *Why:* every model shares the same vocabulary, shapes and builder, so a module per model multiplies the releases and the lists of modules (`new-module.md`, rule 6) for no new meaning; a logical model is a design one level above the tables that implement it, so putting it in their module mixes design with implementation and forces their release on every re-export.
2. **Keep the export exactly as the tool wrote it, in its own file and graph, in the tool's namespace.** In the package it is a file of its own beside the module's Turtle, copied byte for byte, and the package builder must carry such files without merging them into the module's graph or rewriting their header (extend the builder once, if it cannot: `release.md`, rule 8, lists a package's files). Re-mint nothing: no copy of an entity or attribute under the module's namespace, no `skos:exactMatch` from a copy to the original, no entity turned into a SKOS concept. The tool's namespace is not the ontology's, so no namespace rewrite (such as a release that moves the base IRI) touches it. *Why:* the export is the view the modellers recognise and the tool regenerates; a copy doubles every term and has to be brought back into step after each re-export, and an edited export is lost at the next one.
3. **Link the export to the ontology through annotation properties in the module's own namespace.** The layer says, per entity: the model it belongs to (an individual of the module's one class for models), the source system its data comes from, the concept or class it describes, and the platform table or data product that implements it. Point to each target by IRI in the release of its module that the package's closure loads (its `dcterms:requires` pins, resolved as `release.md`, rule 12, resolves them), and fail the build when a target is not in that release; when the module is built against the newest releases, as a first release usually is, the closure and the newest are the same. *Why:* annotations are not part of an ontology's logical meaning (OWL 2 Primer, §8.1), so the tool's classes stay plain classes and no reasoner reads the links as axioms; an object property with a class as its subject would make the class an individual too (punning).
4. **Ship shapes for the layer, and run them with the export and the releases of the package's closure loaded (`release.md`, rule 12),** each with a negative test (`shacl.md`, rules 7 and 8). *Why:* a link to a target of the wrong kind (a concept where a system belongs) is the layer's likeliest defect, and only a shape that sees both ends can catch it.

## Key it so a re-export cannot break it silently

5. **Key the layer on the tool's stable identifier for each entity, never on its IRI when the tool builds IRIs from names.** At each build, find the entity's current IRI from the identifier; fail the build when a row names an identifier no entity in the export has, and when an entity of the export has no row (a new entity must be drafted, even as doubtful, before it ships). Look the identifier up among the entities (the export's classes) only, since a tool may number entities and attributes in one shared sequence. *Why:* a renamed entity gets a new IRI, so links keyed on IRIs would point at nothing and every query would quietly lose that entity; a failed build names the gap instead.
6. **Give each model its own named graph, and fail the build on any IRI that two models both define.** Each model's export and layer stay separate files in the package, so a store loads each as its own named graph; never serialise them into the module's one graph. Exempt only the tool's own vocabulary that every export repeats (its attribute and key classes and its annotation properties), the tool's shared header node, which rule 7 handles in each model's own graph, and a term, such as a glossary term or a reused attribute, that both models describe identically. *Why:* every export uses the same namespace, so two models with an entity of the same name merge into one class without a warning.
7. **Mind the tool's shared header node.** When every export declares the same ontology node, check each header in its own model's graph and never compare headers across models; fail only when an export declares a header other than the tool's. Copy the model's title and creation time onto the model's own individual in the layer, and have every query find a model through the layer, never through the header. Tell a store that loads several models to keep each in its own named graph. *Why:* in one graph the headers merge into one node with every model's title and date, and a query that reads it gives wrong answers.

## The tool's own shapes

8. **Keep the tool's shapes out of the ontology's whole-graph gate when they constrain records, and load them there as data only.** Record the reason in the module's documentation. Where a competency question reads them (which attributes are keys), have the builder check their structure instead: each names a key type, targets one entity of the export, and constrains only that entity's attributes. *Why:* a shape that targets an entity validates that entity's instances, the records (SHACL, §2.1.3.2), and the ontology holds no records (`foundations.md`, policy 2), so over the ontology it checks nothing. A tool's SHACL-SPARQL may also break SHACL's rules: a query's prefixes are declared with `sh:prefixes` (§5.2.1), and a subquery must return every pre-bound variable, `$this` among them (§5.3.1 and Appendix A). An engine may refuse such a shape once a record is present, so test it in yours before you rely on it (`shacl.md`, rule 16).

## Draft the links

9. **Draft the links in a file kept beside the export, one row per entity:** the model, the tool's identifier, the source system, the concept described, the implementing platform table or data product, a status of `asserted` or `doubtful`, and the evidence. Assert only a link the entity's name, description or the tool's own metadata makes clear; mark every other one `doubtful`. Only asserted rows become triples, and the builder prints the doubtful rows with their evidence. *Why:* a guessed link becomes a wrong fact in every answer that follows it, and evidence on each row lets the owner settle it in seconds.
10. **Put every doubtful link before the owner on the page they approve the release from,** and record each answer before the row changes status (`governance.md`, rule 3). *Why:* the release is the owner's to approve, and a doubtful link left out of that page is a decision nobody made.

## Test it

11. **Test the questions about the records a model describes on a made-up example graph** (`new-module.md`, rule 9): a small export written in the tool's own format, its links file, and the graphs the builder makes from them, verified by the check script and never in a package. Where the real export may not enter the repository, the example is made up, not drawn from it. Where the example needs a feature no real export has shown yet (a link from an attribute to a glossary term), mark its form ASSUMED (`governance.md`, rule 3). Give each shape and each builder failure (rules 3 and 5 to 7, and rule 12's changed hash) a test. *Why:* the package alone holds no records, so without an example the questions return nothing and the regression proves nothing.

## A confidential export

12. **Where the export is confidential, keep it outside the repository and let the release build read it from a folder git ignores** (an augment folder) (`governance.md`, rule 24). Record each file's hash in the release's input record (`release-inputs.json`), validate the release from its archive alone and check the folder against that record as `release.md`, "Inputs kept outside Git", says; a re-export ships only as a new release the owner approves, which records the new hash. The release that carries a confidential model is itself confidential: it holds the model's entities and descriptions, so who receives it is the owner's decision (`governance.md`, rule 25). Apply the privacy rules to the module built from it (`governance.md`, rules 23 to 25), including the check script's names check, and give any test that rebuilds the release, rather than validating it, the folder too. The builder takes the export's location as an input, so the same build runs from the main branch once the owner lets a model live there. State in each document whether it counts the modules of the main branch or of the release. *Why:* a committed file stays in history after deletion; the recorded hash, checked against the folder, shows which export a release holds when the file itself is not in the repository; and one builder with a location input keeps the release build and a later main-branch build the same code.
13. **Clean an export that passed through email or a word processor before you use it, and record each change.** Extract the Turtle from any document wrapper; restore every IRI a mail filter rewrote into a tracking link from the original target it encodes; replace non-breaking spaces with plain ones and remove any heading the wrapper added, but leave every character inside a literal as written (curly quotes and accented letters in a description are content); then parse it with an RDF parser and check that every IRI sits in the tool's namespace or a vocabulary you expect, and that the counts of classes and datatype properties match what the tool reports. Keep the cleaned file beside the original, outside the repository, and hash the cleaned one. Ask the owner for a direct export when one is possible. *Why:* a rewritten link is still a well-formed IRI, so a parse alone passes it, and every link the layer makes to that entity would point at a mail filter.

## Release it

14. **Release the module at `1.0.0` only with the ontology owner's approval** (`new-module.md`, rule 4; `release.md`, rule 6), and build it as a candidate until then. A later model added to the module is a minor release (`release.md`, rule 3). A re-export that drops an entity, or renames one where the tool builds IRIs from names, removes an IRI consumers may have pinned, so classify it with the meaning-change test (`release.md`, rules 3 and 4) before you release. *Why:* the first release is the promise every consumer relies on, and a tool's re-export can make a major change look like a refresh.

Done when: the decision record names the module and each model; each export sits unchanged in its own named graph in the tool's namespace, and nothing is re-minted; the layer is keyed on the tool's identifiers and its build fails on a missing entity, a link target missing from the package's closure and an IRI two models define; the tool's shapes stay out of the whole-graph gate with the reason recorded; every doubtful link is answered by the owner or still marked doubtful on the approval page; the module's questions pass on its package plus the made-up example graph; a confidential export stays outside the repository with its hash in the release's input record, checked against the folder; and `1.0.0` carries the ontology owner's approval, with each gate in `new-module.md` met.
