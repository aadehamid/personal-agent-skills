# SHACL validation

Serves Step 9, and the SHACL slice that checks the first release (Step 4). Read it before you write a shape, a shape test or a validation gate, or before you rely on a SHACL feature in a new engine.

Standard: SHACL, W3C Recommendation 20 July 2017, https://www.w3.org/TR/shacl/.

## What to shape, in order

1. **Build a small slice before the first release:** labels present, IDs present, no provisional namespace left, references resolve. If you will project to a property graph, add the checks for its design rules (the `ontology-to-lpg` skill, `scripts/check_projection_rules.py`). *Why:* the first release is then checked by shapes, not only by scripts.
2. **Then add, in this order:** every relationship fact links to its evidence; every controlled value comes from its own list; no definition is typed as an occurrence (`provenance.md`). *Why:* each one catches a failure the slice cannot see.
3. **Carry evidence in the graph as one qualified-relation node per fact**, naming exactly one subject, predicate and object and every supporting source row, and keep the direct triple. Shape both directions: every fact triple has its node, and every node has its triple. Check in the build that each node's rows equal the evidence mapping's rows for that exact fact. *Why:* a shape can see that evidence exists; only the build can see that a well-formed row ID sits on the wrong fact.
4. **Shape every code-list property against its own scheme, and test the coverage:** a test fails when a property takes values from a code list and no shape covers it. *Why:* `sh:class skos:Concept` lets a value from the wrong list through, and a hand-written shapes file misses properties.
Shapes files may use blank nodes (property shapes, `sh:in` lists); the no-blank-node rule covers data only (`identity-taxonomy.md`, Step 2, rule 5).

5. **State a cardinality on every property:** `sh:maxCount 1` on a single-valued one, no maximum on a multi-valued one, including properties declared but not used yet. Test that every property has one. *Why:* the property-graph load reads single or list from it, and an unstated cardinality is a guess.
6. **Use SHACL Core first; use SHACL-SPARQL only where Core cannot express the constraint.** *Why:* Core runs in more engines, and SPARQL targets are the first thing a property-graph engine drops (the `ontology-to-lpg` skill, `references/pipeline.md`, rule 13).

## How to test shapes

7. **Run each module's shapes in its own tests, and run every module's shapes together over the whole graph in one gate.** Every shapes run (a module's, the whole-graph gate, the release-package test) passes only when its report conforms: SHACL makes `sh:conforms` true "if and only if the validation did not produce any validation results" (§3.6.1.1), at any severity. Close a result someone judges acceptable by a recorded decision that changes the data or the shape, never by a note beside the report. Give the gate a negative test with a cross-module break (an overlay node pointing at an undefined item in another module). *Why:* a shape that targets too broadly, or a value one module's shape forbids in another, passes every module's own tests and fails only in the whole graph; and an "explained" result stays in every later report, where nobody can tell it from a new one.
8. **Prove each shape can fail, and make each negative test assert the violation it means:** change one value in a copy of the data, then check the focus node, the source shape or message, and the severity. *Why:* a test that only checks "validation fails" still passes when an unrelated shape fires.
9. **Test that every written release package conforms to its own shapes over its released closure:** the packages its manifest requires, and theirs, loading only the highest version where two paths reach different releases of one module. Pin the list of packages by hand, and fail on any package folder not in it. Add a negative test: a package validated without its closure fails. *Why:* a package that conformed when built can stop conforming once its dependencies are read from the released files.
10. **Test a decided value against the decision, item by item.** Where a shape or script guards values the owner decided per item (a scope, a status, an exception), compare each item's value with the record that decided it; membership in the allowed list is not enough. Negative tests include an allowed value on the wrong item and an exception the record never granted, and assert the decided outcome (for example the severity). *Why:* an allowed value on the wrong row passes every membership check.
11. **When a decision fixes a set, guard the set itself.** If a record decides exactly which processes a lifecycle stage links to, the build and the shapes hold that set, written out by hand, and reject a real value on the wrong item, a missing value and a value that does not exist. *Why:* checking only the kind of value lets a valid value on the wrong item through.
12. **Follow the whole chain in a rule over a hierarchy.** "No role is a subclass of party" is checked with `rdfs:subClassOf+`, not one step. *Why:* otherwise a class two steps down passes.
13. **State each guard's reach exactly, and make the build reject what the shape cannot see.** A shape that targets only nodes holding a link cannot see a node whose links were all removed; say so where the shape is described. *Why:* a reader otherwise trusts a guard for cases it never checks.

## How shapes meet releases

14. **Run shapes written after a release against that release without changing it; they join the release's own shapes at the next release.** *Why:* a released package never changes (`release.md`).
15. **Treat a validation report as data.** A failing shape is a question for a person, not proof of a bad model. *Why:* the shape may be wrong, and only a person can tell which.

## Before you rely on a SHACL feature in a target engine

16. **Test how the engine evaluates each feature you rely on, with one value that must pass and one that must fail**, before you trust its silence. Read the query each constraint compiles to where the engine shows it. *Why:* engines differ from the specification, and a constraint an engine evaluates differently reports a false pass or a false failure.
17. **Anchor every `sh:pattern` at both ends (`^...$`).** SHACL defines `sh:pattern` through the SPARQL `REGEX` function (SHACL §4.4.3), which invokes XPath `fn:matches` (SPARQL 1.1 Query, W3C Recommendation 21 March 2013, §17.4.3.14). `fn:matches` returns true "if $input or some substring of $input matches" the pattern (XPath and XQuery Functions and Operators 3.1, W3C Recommendation 21 March 2017, §5.6.3), so SHACL searches the string. Some engines match the whole string instead: n10s 2025.06.1 compiles `sh:pattern` to Cypher `toString(x) =~ params.theRegex` (`SHACLValidator.java` at tag 2025.06.1, lines 1411 and 1412, https://github.com/neo4j-labs/neosemantics/blob/2025.06.1/src/main/java/n10s/validation/SHACLValidator.java#L1408-L1417), and Cypher's `=~` matches the whole string (Cypher Manual, "String operators"), so an unanchored `"\S"` there fails every value longer than one character. *Why:* an anchored pattern gives the same answer under search and full match.
18. **Prefer IRIs to literals in `sh:in`, and test any literal list in the target engine.** SHACL's own note on `sh:in` says "matching of literals needs to be exact" (§4.8.3). n10s 2025.06.1 reads a literal `sh:in` list as strings (`SHACLValidator.java` at tag 2025.06.1, lines 1044 to 1048, https://github.com/neo4j-labs/neosemantics/blob/2025.06.1/src/main/java/n10s/validation/SHACLValidator.java#L1044-L1048) and tests each stored value with Cypher `val in params.theInLiterals` (line 1359), so a value stored as a boolean or a number is compared with its string form. *Why:* a literal's datatype or loaded form can differ from the shape's, and the engine then reports a violation on valid data.

Which constraints a property-graph engine cannot run, and how the full check is kept: the `ontology-to-lpg` skill, `references/pipeline.md`, rules 13 and 14.
