# Identity and the SKOS taxonomy

Serves Steps 2 and 3. Read it before you mint any IRI, build or regenerate the concept scheme, build a code list, or rename a concept. What kind each term is (concept, class, property, code value) is decided first, in `domain-model.md`.

## Step 2: identity

Record every node in `templates/identity-table.md`.

1. **Slugs and IRIs are identity; labels are presentation.** Never use a label as a join, lookup, access-control or API key. *Why:* labels change and collide; identity must not.
2. **Keep the source's local IDs as `skos:notation` and derive slugs from them. Where a node has no local ID, mint its slug once from the label at the time (lower case, words joined by hyphens), record the date in the identity table, and never change it when the label changes;** where renames are likely, mint an opaque slug (`c0042`) instead. Reference-framework IDs attach by `dcterms:references` and never replace local IDs. *Why:* the local ID is what the business already uses to find the thing, and a minted slug that followed its label would change identity on every rename ("Cool URIs don't change", Tim Berners-Lee, W3C, 1998, https://www.w3.org/Provider/Style/URI).
3. **Put no version in a term IRI; term IRIs are permanent.** Versions live on the ontology header (`release.md`, rule 1). *Why:* identity must survive a definition change, and a consumer who bookmarked a concept IRI must still get a correct answer years later.
4. **Use a persistent base scoped to the organization**, never a person or a project. Until the owner decides hosting, the base identifies and does not resolve (`release.md`, rule 20); the Step 2 gate needs the base recorded, not resolving. *Why:* usernames and project names change; the base should change by one redirect.
5. **Give every node something can point at an IRI, including n-ary and qualified-relation nodes. The ontology's data (each module's and code list's Turtle) has no blank nodes. Shapes files are outside this rule; name them `*-shapes.ttl` so the check script can leave them out.** *Why:* a blank node has no stable identity across builds, so a consumer cannot reference it and a property-graph load cannot reproduce it. Shapes are not data a consumer references, and SHACL builds them from blank nodes: an `sh:in` value is a SHACL list (SHACL, W3C Recommendation 20 July 2017, §4.8.3), which is an RDF list of blank nodes.
6. **Derive minted IRIs of n-ary nodes from content, never from position.** Build an assignment's IRI from its ends plus a short hash of the source string (`.../assignment/lend-item--accountable--circulation-lead--3f9a1c20`), not from its place in a list. *Why:* a source edit that reorders a list must not remint identities.
7. **Settle identity before direction, and direction before meaning.** *Why:* a relationship between two things you cannot identify is a guess.
8. **A label proposes a candidate; it never confirms one.** Resolve a target only on a stable ID or approved contextual evidence; otherwise defer it with the raw phrase, the candidates and a review trigger. *Why:* labels drift during a build and one label can name two concepts in two branches; a label join misresolves both without an error.
9. **Record renames as overlays on the identity map** (current name, prior name, note, scoped alias). After any regeneration of the identity map, restore the overlays before rebuilding the Turtle. *Why:* otherwise the Turtle silently reverts to old labels.
10. **Fix a row's meaning at review time.** If a better reading appears later, hold the row and record the better reading as its reason; corrections reach the source through the source-correction backlog (`promotion.md`, "The release gate"). *Why:* re-reading rows silently makes the evidence ledger unreproducible.

## Step 3: the SKOS taxonomy and code lists

Start from `templates/ontology-skeleton.ttl`.

1. **Use SKOS, not OWL classes, for the naming hierarchy.** One `skos:ConceptScheme`; `skos:broader`/`skos:narrower` for the hierarchy; `skos:prefLabel`, `skos:altLabel`, `skos:notation`, `skos:definition`. Terms whose instances carry properties are classes (`domain-model.md`). *Why:* a subclass axiom "enables reasoners to infer" that every instance of the subclass is an instance of the parent (OWL 2 Primer, Second Edition, §4.2), so every instance joins every ancestor class and anything stated about an ancestor (a restriction, a domain) applies to it; a naming hierarchy intends neither. Disjointness, by contrast, arises only when stated: it "has to be explicitly stated for a reasoning system to make use of it" (§4.3).
2. **Give every concept exactly one parent, except the scheme's top concepts (`skos:topConceptOf`), which have none. No cycles. The build fails on either.** *Why:* the parent test and every roll-up query assume a tree.
3. **Slot every new concept into the hierarchy; allow no floating nodes.** *Why:* a floating node escapes the parent test and every scope query.
4. **One `skos:prefLabel` per language per concept.** Language tags follow `foundations.md`, policy 5. *Why:* SKOS forbids two preferred labels in one language (SKOS Reference, W3C Recommendation 18 August 2009, integrity condition S14, https://www.w3.org/TR/skos-reference/), and two would make the name a coin toss.
5. **Put `skos:definition` on every concept, to the quality bar for its kind (`quality.md`), and a scope note on every approved one.** *Why:* a concept without a definition means whatever each reader assumes.
6. **Send every definition, collected or written, through the human gate in `quality.md`.**
7. **Classify by primary purpose, not by location, asset or department.** Write one primary question per top-level branch (for a library's circulation branch: "how do copies reach members and come back?") and use it as the placement test for every new concept. *Why:* purpose is stable when the org chart and the systems change.
8. **Add aliases selectively.** `skos:altLabel` is a live search commitment: make a former name an alias only if it is unique, accurate and useful. Keep other former names in a history annotation. *Why:* a stale alias returns the wrong concept to a search.
9. **Split a source field that mixes dimensions.** A status column holding "overdue", "returned late" and "overdue/hold pending" mixes a loan's state, its history and another member's hold; model one controlled field per dimension, each with its own code list, and record "unspecified" honestly where a value is missing. *Why:* one mixed field cannot be validated or queried by any one dimension.
10. **Keep lifecycle status, governance status and hold status apart.** Lifecycle is carried by `dcterms:dateAccepted` (approved; absent means candidate) and `owl:deprecated`; a governance or hold status, if the build needs one, is its own code-list property. *Why:* a concept can be a candidate and on hold at once; one status chain cannot say that.
11. **Give every code-list property its own SKOS scheme**, and check each value against its own list (`shacl.md`, rule 4). *Why:* a value from the wrong list (a cadence used as a loan state) passes a check that only asks "is it a concept?".
12. **Give each concept a concept kind where some concepts are not things anyone does or has:** a code-list property (for example `<base>conceptKind`) whose values include "structural anchor", a grouping node that exists only to organize the hierarchy. *Why:* responsibility and run rules must be able to exclude grouping nodes by a query.
13. **Run the mechanical checks before any review, on data files only (rule 5):** `uv run --with rdflib python3 <skill>/scripts/check_taxonomy.py <files>` checks labels, definitions, notations unique per scheme, one parent except top concepts, no cycles, no label collisions, no blank nodes, tagged language literals, an `rdf:type` on every IRI used as a subject, classes written as `owl:Class`, each class's and property's (annotation properties too) label and definition, exactly one property kind, and for object and datatype properties one domain and one range that are IRIs and resolve, with a range that matches the kind. Its docstring lists each check and the namespaces it accepts unresolved. *Why:* a reviewer's time goes to meaning, not to typos a script finds.
14. **Map a source's strings to code-list values (statuses, roles, systems) through a register, one row per string as the source spells it** (`templates/identity-table.md`). Merge two strings only when they differ in case, plural, punctuation, or "&" against "and"; never merge on a guess at what an acronym or a term means, and put any other near-match to the owner. *Why:* a wrong merge gives one value another's meaning, and splitting later costs more than merging later.

Deprecation and release headers: `release.md`.
