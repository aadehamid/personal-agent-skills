# Before every push

Run these before you open a PR and again before every review-fix push. Fixes cause as many misses as first pushes.

1. **The check script passes.** Run the project's check script (for example `scripts/check.sh`). If the project has none, see `guardrails.md`.
2. **Figures come from the shared tool.** Every count, total and ID list is recomputed by the project's tool from the source files, never copied from memory, a summary or an earlier message. Count the population the sentence claims, not a neighbouring one: the listed items, not IDs cited in another item's rationale or explanation.
3. **External facts cite a primary source.** Release notes, a changelog, a specification or a filing, with version and date. An open issue, a roadmap or a search snippet is a lead, not a source. A version claim names the first release with full support, not a preview. For anything hosted on GitHub, read it with `gh api` (releases, tags, file contents). Read the primary source itself, not a page about it: on one PR a README's "Version 1 Beta" heading stood in for an ontology file whose maturity annotation said Released. Quote the governing file or filing, and quote the passage whole: the sentence as the source prints it, so its qualifiers come with it.

4. **A change reaches every place it applies.** Search the whole repo for every status, rule, term or figure you change, including text split across lines. When you change a rule, walk every section that depends on it: later pipeline steps, checklists, examples, companion documents, other repos that copy it. When a change adds a member to a set of values (an enum value, a status, a category) or replaces an instruction, also search for the bare old number, the set's other members, and the old instruction's own words, such as the ticket a step used to wait for. A search for the phrases you expect finds only those phrases. If the project's fact tool has a sweep command, run it first: it lists where the wording the branch replaced or deleted still stands. It cannot see the same claim in other words, a one-word change or an addition, so the searches above stay required. Search record header rows and text split across lines too: on one PR a record's header kept an old count that its body had corrected, and on another a count split across two lines escaped a one-line search. Report what you searched in the PR body, under the heading the project requires (for example "Sweep").
5. **An independent review runs on the diff, and every finding is fixed or answered.** Use a different model from the one that wrote the change. The table under "Who reviews" in `changing.md` says which reviewer to use. When it names Pi, run `~/.agents/skills/way-of-working/scripts/pi-review.sh --role independent --head <commit> --verify "<claims to verify>"`, with `--since <commit>` for a later round, as a background job, and read its report; that section describes the script. When it names the Cursor agent CLI, use `herdr-review.sh --kind cursor`, described below. The table decides the tool; Herdr only decides where it runs. For a reviewer that runs through Herdr, use it when the working agent is inside a Herdr-managed pane (`test "${HERDR_ENV:-}" = 1`), and fall back to the Codex plugin otherwise.

   **Commit the change first, and leave the working tree clean.** A branch review reads committed commits only, so an uncommitted fix is not reviewed at all — an agent that reviews, then edits, then pushes has reviewed the wrong thing. Note the commit you reviewed; if HEAD moves before the push, review again, within the round limit under "Re-review after fixing" below.

   **With Herdr** (the working agent is inside a Herdr pane), spawn a reviewer agent in its own pane — a different kind/model from the writer — and have it run the `ce-code-review` skill, which does a structured multi-agent review (risk-based reviewer selection, parallel reviewers, a cross-model adversarial pass, a validator, and a rendered report). **Reuse the review tab for this repo rather than opening a new one for every review.** Name it `review-<repo>` (the repo's directory name) so it is findable:

      ```sh
      # From the repository under review, as a background job the harness reports back on
      # (Claude Code: run_in_background), never with `&`: a review outlasts a foreground call.
      ~/.agents/skills/way-of-working/scripts/herdr-review.sh --branch <branch> --verify "<claims to verify>"
      ```

      `scripts/herdr-review.sh` opens or reuses the `review-<repo>` tab in this agent's own workspace and starts a reviewer only in an empty pane. The default reviewer is Codex on gpt-6.1-sol at medium reasoning, the owner's choice, set in the script. When the owner asks for another reviewer, `--kind` and `--model` pick it, and it runs in its own `review-<repo>-<kind>-<hash>` tab, where the hash comes from the kind and model. Each kind starts with its own flags:
      - **Codex:** `-a never` (no approval prompts) and the `workspace-write` sandbox with network. The sandbox may also write to `~/.npm`, `~/.claude`, `~/.cache` and `~/.config`, which the review skill's cross-model pass needs.
      - **Cursor** (`--kind cursor`, default model cursor-grok-4.6-medium): `--sandbox enabled --force --trust`, which is sandboxed, with no approval prompts and the workspace trusted.
      - **Kimi** (`--kind kimi`, default model kimi-code/k3): `-y`. Kimi has no sandbox, and `-y` still asks before risky actions. A fresh Kimi can ask a one-time setup question, such as migrating `kimi-cli` data, that blocks the first prompt. Leave that choice to the owner, answer it with `herdr agent send-keys`, and run the script again.

      The script then tells the reviewer to apply the repository's review standards, waits until the reviewer is idle with its report written, and prints the report. Before it prompts, it prints `Report file: <path>` on standard error, so the report stays findable when the output is cut short. Whatever the prompt returns (completed, stalled, blocked or timed out), the script runs one recovery, so a review finishes unattended:
      - **A Cursor prompt left pasted but unsent** (the input line reads `→ [Pasted text #1 +1 lines]`) gets an Enter. The script reads the visible screen on every poll until the reviewer starts work, whatever the status says, and sends Enter on each poll where the input line still shows the marker, up to three Enters. It acts only for `--kind cursor` and only on the input line, so the marker quoted elsewhere on screen, such as in a diff, sends nothing. On 2026-10-23 herdr read the pane as idle, and the text appeared after the first look.
      - **It waits** until the reviewer has worked and gone idle, within 60 minutes of the start.
      - **A reviewer idle without the report** is asked once to write it at the path.
      - **However the wait ends**, a non-empty file the reviewer wrote at the path is printed once its size holds steady, and is never overwritten. The script gives a missing or empty file a minute to fill.
      - **Still missing or empty:** it copies a `report.md` that `ce-code-review` saved under `/tmp` or `$TMPDIR` (`compound-engineering-<uid>/ce-code-review/<run>/`), says so on standard error, and prints it. The script header states which one counts: one written after the script started, whose `metadata.json` names this branch and the commit the script started on, and only when exactly one qualifies. Zero or several end in exit 1.

      **An earlier review can hold the reviewer's name.** Herdr refuses a name another live agent holds and names the holder's tab, directory and status. When the holder is in this work tree and idle or done, the script closes its tab (`herdr tab close`), prints `closed <tab> (status <status>)` on standard error, and starts once more. That retry always runs: closing the holder restarts the five tries a busy pane gets, and a close that fails prints herdr's error and retries anyway. The holder can be the reused review tab itself, whose pane reads as having no reviewer while herdr still holds the name; the script then closes that tab, creates a fresh one, prints `Review tab: <tab id> (created)`, and starts there. When it is still working or blocked, the script stops without closing it: `Reviewer did not start: another review is running in <tab>; wait for it or close it.`, then a `Next:` line that waits for that review and runs the script again. A holder in another directory is left alone, and the start fails with herdr's error.

      Exit 0 means the report, and only the report, is on standard output. Exit 1 means no report, and every exit 1 ends with two lines: the reason, then `Next: <command>`. After the prompt, the output ends with `Prompt result: <herdr error>` (only if the prompt did not complete), the pane's recent text, then `No report at <path>: <reason>.` and the `Next:` line. Before the prompt, a reviewer that did not start prints herdr's error and the pane, then `Reviewer did not start: <reason>.` and the `Next:` line. Any other early failure (`HERDR_WORKSPACE_ID` unset, a herdr error, no review tab or pane, an unwritable report folder) prints its error on standard error, then `No review: <step> failed; the error is above.` and the `Next:` line. The same two lines end a run that fails or is killed after the prompt, with `Next:` set to wait for that review and print its report. Exit 2 means bad arguments. `scripts/test_herdr_review.py` covers each of those cases.

      **Wait for the job's exit status and output before you push or open a pull request.** Launching it returns neither. A non-zero status stops the push. **When it ends without a report**, read the reason, act on it, and run the `Next:` command: `herdr agent wait ... && cat '<path>'` when the review may still be running; `cat '<path>'` when the reviewer's file was still growing; the script again with the same arguments when the reviewer never started or finished without a report; an answer to the reviewer's question (`herdr agent send-keys <pane> <key>`) followed by the wait when it blocked after working, or by the script again when it was blocked before the prompt arrived; and, when several skill reports match, a `cp` of the one you pick after reading them. The review tab shares the working tree, so the reviewer sees the branch you have checked out. For later rounds, run it again with the new commit and say which findings you fixed or answered (see "Re-review after fixing" below). `ce-code-review` is report-only, so apply its findings yourself.

      Setup notes:
      - **The writer can drive the reviewer only with an allow rule.** Claude Code's auto mode blocks starting or prompting an agent that never asks for approval. The owner adds `Bash(herdr agent:*)` once per machine through `/permissions`.
      - **`-a never` stops command-approval prompts.** Execution failures go back to the reviewer instead, so the owner is never asked to approve its commands.
      - **The cross-model pass needs those writable folders.** Under plain `workspace-write`, `ce-code-review`'s Claude cross-check failed with `npm error code EPERM` on `~/.npm`, so the review fell back to an adversarial pass from the same model family. The folders clear that error: on 2026-10-13, `npx -y acpx@0.19.4 --version` failed with EPERM in the plain sandbox and printed `0.19.4` with the folders. That check does not prove the whole cross-model pass runs. If a report says it did not run, say so in the PR body.
      - **A review tab opened before this setting keeps its old sandbox.** The script says so when it reuses a running reviewer. Close that tab once (`herdr tab close <tab id>`), and the next run starts a reviewer with the current flags.

      **Close the review tab when the PR merges.** The script prints `Review tab: <tab id> (created|reused)` on standard error. If this agent's run created it, send the reviewer a "PR merged" message, then `herdr tab close <tab id>`. Do not close a tab you did not create.

   **Without Herdr** (the working agent is not inside a Herdr pane), use the Codex plugin:

   ```sh
   node "$(ls -d "$HOME"/.claude/plugins/cache/openai-codex/codex/*/scripts/codex-companion.mjs | tail -1)" \
     adversarial-review --wait --base main --scope branch "<what to verify>"
   ```

   Tell it which claims to verify and which documents must stay consistent. Ask it to be adversarial, and to say how the thing under review could still pass while being wrong.

   - **State claims as the change's effects, not as your search.** Name what the change does to the project, in this PR's own terms. For example, a PR that adds an order status and drops a manual approval step should claim "orders gain a status; refunds no longer wait for manual approval", not "every document stating the counts was updated". The reviewer checks what the claim names, so a claim that describes your search confines the review to the places you already looked.
   - **Reproduce every finding before you accept it.** A finding is a claim; run it. A finding accepted on assertion becomes a wrong change.
   - **Fix every place a finding applies, not only the one it names.** Before you fix a finding, name its kind, such as a wording, a rule, or a value crossing a boundary, and search the whole repository for it with the project's search tool. Fix every instance in the same commit, and tell the next round the kind and the search you ran. The review scripts ask the reviewer for the same list, but a reviewer can judge one instance fine and leave it out. One PR took three holds this way, each on a named reference crossing a different validation stage; another took a hold for a gate's scope fixed in two of the three documents that stated it.
   - **Fix clear defects; answer judgement calls in the PR body.** Say which is which, so the reviewer can weigh the judgement.
   - **Re-review after fixing, at most two rounds.** A fix can introduce its own defects — a guard tightened in one place is often loosened in another — so run the review again on the fixed diff. A round is one independent review of the branch's head. The limit applies per batch of work:
     - Before the pull request opens, at most two rounds.
     - Each HOLD on the open pull request starts a fresh count of two for the fixes it asks for.

     After the second round of a batch, fix only a finding that would let a wrong result through on input the project will realistically see. List every other finding in the PR body as a follow-up. Push the last fix without another review, and name that unreviewed commit in the PR body. If round two finds the same kind of defect as round one, redesign (next point) instead of patching a third time.
   - **Redesign when tightening a rule starts flagging a *correct* case.** That is the stop signal: a rule tightened to catch one variant of a defect now fails on a case which is right, and no further tightening converges from there — each attempt buys another review round. Change the design instead: what the rule reads, or where in the flow it sits. Say in the PR what design changed and why, then re-check the old variants under the new shape. Until that redesign lands, variants of one wrong design are not separate bugs to be filed away — three copies of a stale figure are three real defects, and they stay defects. A redesign forced by round two gets one review of its own. That is the only review past the limit.

## Prove a new check fails

When you add a check, break the thing it checks on purpose (change one figure, one status, one record) and confirm the check fails; then restore it. A check that has never failed may pass vacuously.

Clear the interpreter's bytecode cache (`__pycache__` for Python) before each run of a mutation and after restoring it. A mutation the same length as the line it replaces, restored within the same second, can leave a cached copy of the mutant that the next run executes, so a correct tree fails or a broken one passes.

Test the check against the cases it claims, not just the happy path: a guard that hashes names rather than contents, or that follows a symlink, or that reads a file named `-` as standard input, passes every ordinary run and fails none. Enumerate the cases the check claims to catch and make each one fail on purpose.

When the cases form a class of input, such as any character or any spelling a renderer accepts, state the rule on what the renderer produces, not on the source text. Then generate the class in the test: every candidate character at every position. A list of the spellings you thought of is what a reviewer extends one round at a time. One check that a quoted answer renders as plain text took nine review rounds this way, most rounds finding another way to hide markup (indentation, a nested quote, zero-width and control characters). It converged only once the rule read the parser's output. The review that passed it tried every code point at nine positions, a probe the test should have run from the start.

Confirm the test run finished before you read its result, from the runner's own final lines (for example `Ran 95 tests` and `FAILED (failures=20)`), not from a count of its output. A run that never starts or never finishes prints no final result, and a count piped from it still prints a number. One test meant to fail on the unfixed code read as zero failures because the command wrapping it was not installed, so `grep -c` counted the shell's error message. Run without the wrapper, it reported twenty failures.

A test that **reproduces a defect** is held to the same standard: run it against the unfixed code and confirm it fails, for the reason you expect. That is not a rule for every new test. A compatibility or invariant test — a valid input still works, the same answer survives reformatting — passes both versions, and forcing it to fail would delete exactly the coverage `guardrails.md` asks for. But that holds only while the invariant already holds on the unfixed code. When the defect *is* that it does not — reformatting changes the answer — the test must fail there, and it is a defect test like any other.

Watch too for a test that passes for the wrong reason: the input that looks like the bug is not always the one that exercises it.

Take a check that reads backticked spans in documents and treats a digest-shaped one as a pin to verify. It must leave `docker compose up …` alone, where `…` means "and so on", so a test asserts exactly that — and it passed, on a span written the way the docs show it, `! docker compose up …`. The check removes the whitespace inside a span before asking whether the span is a pin at all, and the shell's `!` is no digit or letter, so that span failed on its first character and was never judged. The `!` was doing the work; the ellipsis was never tested. Drop the `!` and the same words join into `dockercomposeup…`, which passes for a digest, and the build fails on a documentation line — the case the test existed to cover. Same words, one character apart, and the assertion held in both runs for reasons that had nothing to do with each other.

So state the input and the assertion, then say why the assertion held. If the reason is not the one you meant to test, the input is wrong.

A test that checks data against a document (a fixture against its specification, a generated file against the table it encodes) compares every fact the document states, not just the identifiers. Comparing names and connections lets a wrong type, value or reference through. Two more steps close the gap:

- **Forbid facts the document does not state.** Compare whole records for exact equality, so an invented value fails.
- **Pin the document text the data was last checked against,** by hash, so any edit to that text fails the test until someone checks the data again. A parser reads only the facts it was written for and cannot notice an edit to the rest; the pin can.

## Done when

All five hold, and the PR body says that they ran and what the review found.
